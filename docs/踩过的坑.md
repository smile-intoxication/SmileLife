### ⚠️ 踩过的坑（务必别再犯）

1. **小组件是独立 target**：用到的共享类型必须放在 `watch/Shared` 并加进它的 sources，
   否则 `cannot find type '...' in scope`
2. **Swift 不允许把 `#if` 写在数组字面量里**（`#if` 是「声明」，数组元素位置要「表达式」），
   会报 `expected expression in container literal` 并引发几十条级联语法错误。
   正确做法：用承载条件编译的计算属性，再用 `+` 拼接到数组上
3. **不要把 `FileManager.replaceItemAt` 当原子写用**：它要求目标文件**已存在**
   （参数名就叫 `originalItemURL`）。首次运行时目标不存在 → 抛错 → 若被 `try?` 吞掉，
   文件就**永远创建不出来**，之后每次写入都失败，且没有任何报错。
   正确做法：`Data.write(to:options:.atomic)`（本身就是同目录临时文件 + rename）
4. **HealthKit 的读权限是不可查询的**：`authorizationStatus(for:)` 只反映**写入**授权，
   只读 app（`toShare` 为空）拿它判断会**永远**显示"未授权"。只能靠查询结果反推。
5. **XcodeGen 会把版本号硬编码**：`CFBundleShortVersionString`/`CFBundleVersion` 默认被写成
   字面量 `"1.0"`/`"1"`，**不显式设成 `$(MARKETING_VERSION)` 的话，改版本号对产物完全无效**
6. **必须有 `PrivacyInfo.xcprivacy`**：Apple 规定 2024-05-01 起，用到 required reason API
   （我们用 `UserDefaults`）却没在隐私清单里声明的 app，**App Store Connect 直接不接受**。
   三个 target 各放了一份（手表 app 声明 `CA92.1`，另外两个为空）
7. **CI 两个 job 必须用同一套编译设置**：`compile` 里探测 SDK 并定义 `HAS_WATCHOS_27_SDK`，
   但 `testflight` 的 archive 一开始没做同样的探测 → 会出现「CI 验证过的配置 ≠ 实际发货的配置」
8. 🔴 **诊断 Issue 的触发条件必须是 `failure() || steps.build.outcome == 'failure'`**（**两个都要**）：
   - 只写 `steps.build.outcome == 'failure'`：brew / xcode-select / xcodegen / SDK 探测失败时
     `steps.build` 是 **skipped**，诊断完全不会跑；
   - 只写 `failure()`：**编译步骤带 `continue-on-error: true`，它的失败会被掩掉**，
     此后所有步骤看到的 `failure()` 都是 **false** —— 于是**编译失败时 Issue 永远不会建**，
     而那恰恰是最需要远程诊断的情况。实测 run #26 就是这样：仓库里连 Issue 都没有，
     只能让用户手动下载 artifact 日志。
   - 注意 `outcome` 与 `conclusion` 的区别：`outcome` 是应用 continue-on-error **之前**的结果。
   - 自检脚本第 8 节现在会断言这两处条件同时存在。
9. **`ExportOptions.plist` 里 `destination=upload` 不会留下 `.ipa`**：
   对应的 artifact 步骤不能用 `if-no-files-found: error`，否则会出现
   「TestFlight 上传成功了但 job 变红」这种最坏的信号
10. **workflow 的 `run:` 块本质是字符串**，在 Windows 上编辑它**没有任何反馈**：
    一个多余的 `{` 要等到 macOS runner 上才炸。而且如果炸在**诊断步骤**里，
    会连带把真正的失败原因一起吞掉（run #6：断言失败 → 诊断脚本语法错 → 无 Issue）。
    ✅ **推送前必须跑 `bash ci/verify-project.sh`**，它第 8 节会提取每个 `run:` 块做 `bash -n`
11. **诊断/上报步骤必须比被诊断的代码更宽容**：开头 `set +e`、容忍输入文件不存在、
    容忍 `grep` 无匹配。判断"有没有 error"的 `grep` 在**没有** error 时返回 1，
    在 `bash -e` 下会直接让诊断步骤失败
12. **GitHub Issue 正文上限 65536 字符**，超了 `gh issue create` 直接拒绝 ——
    而这恰好发生在"正在报错"的时候。要 `head -c 60000` 截断
13. **不要硬编码构建产物名**：watch app 产物名由 **target 名**派生
    （target `AppleWatchHealth Watch App` → `AppleWatchHealth Watch App.app`，注意没有空格分隔 AppleWatchHealth）。
    手写极易出错（第一次就写成了 `AppleWatch Health App.app`）。
    正确做法：`find "$APP/Watch" -maxdepth 1 -name '*.app'` 在预期目录里找
14. 🔴 **archive 成功 ≠ export 成功**（run #10 踩到）：
    - `xcodebuild archive` 只用**开发**证书就够，所以会看到
      `Signing Identity: "Apple Development: Created via API (...)"` 和 `** ARCHIVE SUCCEEDED **`
    - 但 `-exportArchive` 到 App Store **必须**用**分发**证书
    - 而 **cloud-managed distribution certificate 需要 Admin 角色的 Team Key**，
      **App Manager 不够**；**Individual Keys 完全不支持云端签名**
    - 症状：`error: exportArchive Cloud signing permission error`
      + `error: exportArchive No profiles for '<bundle id>' were found`
    - 依据：Apple 开发者论坛 thread **810658** / **698117**
    - ⚠️ 不要被 archive 日志里的 `ARCHIVE SUCCEEDED` 误导成"签名没问题"
15. **能力（capability）要分两步**：先在门户**注册**（如 App Groups），再**逐个 App ID 分配**。
    而且只有**真正用到它的 target** 才会报错 —— run #8 里 iOS app 因为 entitlements 为空所以不报错，
    很容易误判成"只差一点点"
16. 🔴 **必须有 App 图标**（run #12 踩到）：项目从零手写起来时最容易整个漏掉。
    表现很有迷惑性——**签名全过、`.ipa` 都开始上传了**，最后被 **App Store Connect 服务端校验**打回：
    `Missing required icon file`（缺 120x120）/ `Missing Info.plist value 'CFBundleIconName'` /
    `Missing Icons. No icons found for watch application`
    - 走 Apple 的 **single size** 方案：iOS 和 watchOS 各放**一张 1024x1024**，
      actool 自动派生全部尺寸（官方文档 "Configuring your app icon using an asset catalog"）
    - ⚠️ **`ASSETCATALOG_COMPILER_APPICON_NAME: AppIcon` 必须显式写** ——
      XcodeGen **不会**替你设（只有 Xcode 新建工程模板才带）。不设的话 actool 收不到 `--app-icon`，
      既不生成 `CFBundleIconName`、也不派生 120x120
    - 生成脚本：`python ci/make-app-icon.py`（可复现、可 diff，优于往仓库塞二进制 PNG）
17. **图标不能有 alpha 通道**：App Store 明确拒收（"can't be transparent nor contain an alpha channel"）。
    PNG 的 IHDR 第 25 字节是 color type，**2 = RGB（对）**、**6 = RGBA（会被拒）**。
    自检脚本第 9 节直接读这个字节判断，不依赖任何图像库
18. 🔴 **不要用「依赖 runner SDK 版本」的编译条件去门控新 API** —— 这是「**绿着但错的**」典型：
    RMSSD 曾被 `#if HAS_WATCHOS_27_SDK` 门控，而 CI runner 只有 watchOS 26.2 SDK，
    **那个条件从未成立** → RMSSD **从来没被编进任何产物**，而 CI 一直是绿的。
    ✅ 正确做法：**用原始字符串构造类型标识符**
    （`HKQuantityTypeIdentifier` 是 ObjC 的 `NS_TYPED_ENUM`，Swift 里是 `RawRepresentable` 结构体，
    `rawValue` 就是 ObjC 常量名）：
    ```swift
    HKQuantityType.quantityType(forIdentifier:
        HKQuantityTypeIdentifier(rawValue: "HKQuantityTypeIdentifierHeartRateVariabilityRMSSD"))
    ```
    老 SDK 照样编译、watchOS 27 上运行时可用。
    ⚠️ 代价：字符串写错**不会编译报错**，只会返回 nil → 所以**绝不强制解包**（guard let 后跳过），
    自检脚本第 10 节守住这一点
19. **`CFBundleDisplayName` 才是桌面/表盘上显示的名字**（三个 target 各自一份，现在是「长明护心」）。
    它和 App Store 的**商店名称**是两回事 —— 后者在 App Store Connect 里设置
20. 🔴 **手表 → 手机必须用 `transferUserInfo`，不能用 `sendMessage`**：
    `sendMessage` 要求 `isReachable == true`，而手表在后台跑那几秒里
    iPhone 几乎**永远不可达** → 每次同步都白跑，而且**丢得完全安静**。
    `transferUserInfo` 不需要对端可达，且系统会持久化队列（app 被杀也会送达）。
    自检脚本第 13 节把「代码里出现 sendMessage」直接判失败。
    ⚠️ 代价：Apple **没有公布** `transferUserInfo` 的大小上限，
    社区出现过 `PayloadTooLarge`，所以按 32 KB / 200 条保守分批。
21. 🔴 **WCSession 必须在启动最早的时候激活，不能放在 SwiftUI 视图里**：
    手表在后台把数据传过来时，**手机上的 app 可能从来没被打开过** ——
    那种情况下系统走 launch 路径，任何视图都不会被创建，放在 `.task` 里正好错过。
    手机端因此必须用 `@UIApplicationDelegateAdaptor` 挂出 `didFinishLaunchingWithOptions`。
    症状极其难查：**界面上什么都正常，就是数据不来**。
22. 🔴 **换手表时必须重新 `activate()`**（`sessionDidDeactivate` 里）：
    不重新激活的话，用户换了手表之后新表的数据**永远收不到**，
    而旧的会话仍然报告自己是 `activated` —— 界面上一切正常。
23. **手机端的幂等去重靠 `@Attribute(.unique) var uuid`**：
    这是手表能"不确定就重发"的前提。去掉它**不会编译报错**，
    表现是"重发一次就多一条重复数据"。汇总桶的合成键 `key` 同理
    （去掉的话同一时间桶会出现多行，图表数值凭空翻倍）。
24. **汇总桶要用「按受影响范围重算」，不要用增量加减**：
    增量要求我们知道"这条是新增还是覆盖、覆盖前旧值多少"，这些状态一旦在传输中丢失
    （重发、乱序、app 被杀）桶就**永久偏移且无法发现**。重算只多一次按索引的范围查询。
25. **删除转发与保留清理是两回事**（很容易被当成同一件事"顺手修掉"）：
    `HKDeletedObject` = 用户主动删了 → 手机**跟着删**；
    `enforceRetention` 删本地 = 手表磁盘放不下 → 手机**不能删**（手机是长期档案）。
    把保留清理也转发出去，会变成"手机上永远只有 7 天数据"。
26. 🔴 **`WCSession` 的属性在 iOS 与 watchOS 上不对称**，用错方向**只会在编译另一个平台时报错**：
    - **iOS 专属**：`isPaired`、`isWatchAppInstalled`（头文件标了 `__WATCHOS_UNAVAILABLE`）
    - **watchOS 专属**：`isCompanionAppInstalled`（`__IOS_UNAVAILABLE`）
    - 两边都有：`isReachable`、`outstandingUserInfoTransfers`、`activationState`

    实测踩到过：手表端写了一行 `session?.isPaired`，CI 报
    `error: 'isPaired' is unavailable in watchOS`（Issue #5）——
    对一个只属于某个 target 的文件来说，那就是它**第一次被编译**的时候。
    自检脚本第 14 节两个方向都查。
27. 🔴 **SwiftUI 的类型推导会「超时」**，而这类错误**只有编译器能发现**（Windows 上完全看不出来）：
    把「`ForEach` 套 `ForEach` + `if let` + 字符串插值 + 泛型 Mark」
    一起写进 `Chart { }`，编译器直接放弃：
    ```
    error: the compiler is unable to type-check this expression in reasonable time;
           try breaking up the expression into distinct sub-expressions
    ```
    ✅ **数据先拍平成字段类型写死的数组，视图里只留一层 `ForEach` + 一个 Mark**
    （见 `SleepChartSegment` / `ChartSeriesBuilder.sleepSegments`）。
    顺带的好处：业务规则（"小于 36 秒的碎片不画"）从视图层挪到了数据层。
    ⚠️ 同类风险还有 `Menu { } label: { 一长串带修饰符的视图 }`、
    `Text("…\(a)…" + "…\(b)…")` —— 都拆成独立的计算属性更稳。
28. **`ios/` 里的文件只有 iOS target 被编译时才会报错**：
    编译是按 target 顺序来的，**watch app 先编**。所以 watch app 一旦失败，
    iOS target **根本不会开始编译** —— 看起来"改了半天没进展"，
    其实是错误被前一个 target 挡住了。
    判据：编译日志里搜不到 `ChartView.swift` / `PhoneStore.swift` 这些 iOS 文件名。
29. 🔴 **探针查的类型必须在 `readTypes` 里，否则它报的「0」毫无意义 —— 而且会伪装成事实**：
    HealthKit 对**没授权的类型返回空数组、不返回错误**，所以"没权限"和"设备没这个数据"
    在界面上**长得一模一样**。
    实测踩到过：`HKSeriesType.heartbeat()`（心跳序列）是 **`HKSeriesType`，不是 `HKQuantityType`**，
    进不了 `MetricCatalog.all` 那张指标表，于是**从来没被加进 `readTypes`**。
    v1.7 的诊断界面因此报「近 7 天 0 条序列」，**差点被当成实测证据**写进调研文档，
    得出"房颤历史关闭时手表不写逐拍数据"的结论。
    这类 bug **不报错、不崩、界面完全正常**，输出却伪装成"事实" —— 比崩溃危险得多。
    ✅ 改法：类型只在**一处**定义（`MetricCatalog.heartbeatSeriesType`），
    探针不许就地构造（否则会出现"申请 A、查 B"，同样只返回空数组）。
    自检脚本第 15 节守这三条。
30. 🔴🔴 **授权未决时推进同步游标 = 静默永久丢历史**（本项目发现的最隐蔽的一个）：
    HealthKit 对**没授权**的类型返回**空数组 + 一个有效的新 `HKQueryAnchor`**。
    于是：后台刷新在用户点授权之前先跑一轮 → 每个类型都"成功"返回 0 条 + 新游标
    → 游标被推进 → 用户之后授权成功，从那个游标往后查**只会拿到新数据**，
    授权之前那段历史**永远补不回来，而且零报错**。
    v1.8 新增「心跳序列」读权限时这条路径一定会被走到（后台任务可能先于用户操作）。
    ✅ 修法：`HealthAuthorizer.isAuthorizationPending()` +
    游标落盘受 `canAdvanceAnchor` 保护。
    ⚠️ 细节：**内存游标必须始终前进**，否则同一轮的分页会反复拉同一页（死循环）；
    只有"落盘"要看授权。自检脚本第 15 节守这一条。
31. **线协议新字段必须写成 `Optional`，不能靠"给个默认值"**：
    Swift 合成的 `Decodable` 对**非可选**属性用 `decode` 而不是 `decodeIfPresent`
    —— 也就是 `var x: [T] = []` **不能**容忍缺失的键，老版本一解码就抛错、
    **整批数据丢掉**（而不是忽略新字段）。只有真写成 `Optional` 才走 `decodeIfPresent`。
    自检脚本第 13 节守这一条。
32. **SDNN 必须用 NN 间期算，不能用原始间期**：
    SDNN 的定义是 **NN（normal-to-normal）间期**的标准差，而早搏会把 SDNN
    显著**拉大** —— 这是 SDNN 虚高最常见的原因。
    而且过滤开关必须**和图联动**，否则同一屏上会出现"图变了、数字没变"的矛盾。
33. **不要静默截断**：有上限是对的（内存/渲染），但**必须把"截断了"回报到界面上**。
    静默丢弃比报错更糟 —— 用户会以为"数据就这么多"，
    于是任何"图看着不对"的排查都从错误的方向开始。
34. **编辑大块代码后做一次"悬空引用检查"**：
    实测有一次工具调用被截断，只写进了半段代码 ——
    结果是 `body` 引用了一个**不存在的** `poincareContent`，
    这种错误本地看不出来、只有 CI 会报。改完大文件后顺手数一遍
    "关键符号的定义次数 / 引用次数"是否配对（用 grep 数），几秒钟的事。
35. 🔴 **图表形态必须由体征决定，不能一律折线**（需求方明确要求过）：
    判断依据是「**数据是怎么产生的**」，不是好不好看 —— 用错图**会让图说谎**：
    · 血氧 / 呼吸频率 / 腕温是**离散点测**，连线等于把"中间没测"伪装成平滑过渡；
    · 活动能量 / 锻炼时间是**日累计量**，画成平均值折线会和活动圆环完全对不上；
    · 心率才是唯一真正连续高频的，折线 + 波动带配它。
    实现在 `MetricDisplay.ChartStyle`（`shared/`，和标题/单位同级）。
    ⚠️ **`chartStyles` 表有 `?? .line` 兜底 —— 漏一个指标不会报错，
    只会让那个体征悄悄退回折线图**。自检脚本第 12 节两个方向都查。
    ⚠️ 守这个不变量的判据要用「**字典键**形式」（`"id": .xxx`）：
    第一版只数 `"id"` 出现的次数，而 `sleep_analysis` 在 `categoryLabel` 里
    也出现过一次，计数虚高会把漏配**掩盖掉**。
36. 🔴 **柱状图的"天"必须用 `Calendar.startOfDay` 对齐，不能用 epoch 取模**：
    epoch 对齐的"天"是 **UTC 午夜**，在东八区就是**早上 8 点** ——
    "一天的活动能量"实际统计的是 08:00–08:00，和用户的日界线（以及活动圆环）对不上，
    **而且完全是静默的**（图还是画得出来，只是数是错的）。
    小时可以用 epoch 取模：所有真实时区的偏移都是 15 分钟的整数倍。
    同理，柱状图的聚合粒度（`ChartRange.barBucket`）**不能复用折线的 `displayBucket`**
    —— 活动能量按 15 分钟切会变成 96 根柱子，日总量直接看不出来。
37. 🔴🔴 **云端签名每跑一次 CI 就新建一张开发证书，额度会被发布次数攒满** ——
    而失败信息完全指不到这个原因（看起来像签名/描述文件坏了）：
    ```
    error: Choose a certificate to revoke. Your account has reached the
           maximum number of certificates. To create a new one, you must
           choose a certificate to revoke.
    error: No profiles for '<bundle id>' were found
    ```
    **根因**：GitHub runner **每次都是全新机器、keychain 里没有任何私钥**，
    云端签名（`-allowProvisioningUpdates`）复用不了已有证书，
    只能在 Apple 那边**新造一对密钥 + 一张证书**。
    实测：v2.1 挂掉时账号上积了 **12 张**开发证书、全部叫 "Created via API"、
    **一张分发证书都没有** —— 对着 tag 数一下就是"每发布一次一张"，不是偶发故障。

    ✅ **处理**（两步都要做）：
    - **一次性**：吊销旧的（只动 `DEVELOPMENT` + `"Created via API"`，保留最新 2 张）
    - **长期**：`ci/prune-dev-certs.py` 在 Archive **之前**跑 ——

38. **`private` 在文件作用域下等于 `fileprivate`，而「内部类型不能暴露文件私有类型」**：

           'ChartPickerItem' uses a private type

    原则：**谁能看见谁**要显式想一遍，别默认"同一个文件里就没关系"。

    而 `[IO.File]::ReadAllLines(..., UTF8)` 读到 **932 行** ——
    **两个工具对同一个文件的行数不一致**。照行号切的结果是：
    **删掉了完全无关的两节（§五、§六）、指针插错位置、而想搬的那节还在原地。**

       这次能全身而退**完全靠它**，30 秒就恢复了。
    2. **用内容锚点定位，不要用行号**：
       ```powershell
       $a = $t.IndexOf('### 📚 里程碑详情')
       $b = $t.IndexOf('### 怎么验证改动')
       $new = $t.Substring(0, $a) + $pointer + $t.Substring($b)
       ```
    3. **写完先校验、再落盘**：断言"该有的小节都还在"+"该删的确实没了"，
       任一条不满足就 `throw`。**校验放在写入之前** —— 这样失败时原文件根本不会被碰

       但因为有校验，文件毫发无损）。

    📌 一般化的教训：**两个工具对同一份事实给出不同答案时，先停下**，
    换一个不依赖那个事实的方法（这里是"改用内容定位"），而不是挑一个信。

42. 🔴 **Apple 明确给了"这一拍前面漏了拍"的信号，而我们把它丢掉了**（又一个"伪装成事实"级的静默错误）：
    `HKHeartbeatSeriesQuery` 回调的**第三个参数**是 `precededByGap`，官方原文：
    > "…whether this heartbeat was **immediately preceded by a gap in the data**,
    > indicating that **one or more heartbeats may be missing**."

    也就是说：**这一拍和前一拍的时间差，不是一个真实的心跳间隔**。
    而我们的 RR 间期正是"相邻时间戳相减"算出来的 —— 之前写的是
    `{ _, timeSinceStart, _, done, error in`，第三个 `_` 就是它。

    **为什么危险**：漏 1 拍会把 800 ms 变成 1600 ms，而 1600 ms **正好落在**
    手机端 300–2000 ms 的生理范围内 → 它会被当成一个真实的心跳间隔画进散点图，
    同时把 SDNN 拉大。**不报错、不崩、图也画得出来**，还会被当成"早搏"。

    ✅ 修法（v3.2）：洞标记**与时间戳成对采集**（`watch/Health/HeartbeatReader.swift`
    是 `HKHeartbeatSeriesQuery` 的**唯一**调用点）→ 每拍 1 bit 落库 →
    线上协议加 **Optional** 字段 → 手机**按洞切段后再配对**，并**如实回报**
    "跨洞丢弃 N 个"（自检第 16b 节守 4 条：唯一调用点 / 确实收了 / 字段是 Optional / 真的在用）。

    📌 **三条一般化的教训**：
    - **"官方给了信号但我们没收"比"官方没给"更常见**：回调里的布尔参数、`count`、
      `metadata` 都要逐个看一遍，别用 `_` 搪塞。
    - ⚠️ **守卫的判据别用裸子串**：自检第 14 节查的是"手表端用了 WCSession 的
      iOS 专属属性 `isPaired`"，判据就是**裸名字**；我在 `HeartbeatReader.Beats` 里
      加了个 `var isPaired: Bool`（本意是"两个数组长度对齐"），
      **直接把自检判红了一次纯误报**。改成「成员访问」形式（名字前面带一个点）才对 ——
      真正的违规形态一定是 `session?.isPaired`。**守卫一旦误报，久而久之就没人信它了。**
    - **"官方没写"的结论要定期复核**：仓库里原来写着"官方从未说手表会自动产生心跳序列"，
      而官方在 `HKMetadataKeyAlgorithmVersion` 的 Note 里其实正面回答了：
      "In watchOS 8, the system uses this key for heartRateVariabilitySDNN and
      **HKHeartbeatSeriesSample** samples **generated by Apple Watch**"。
      诊断页现在就用这个键判断"是不是系统产的"。
